01 PRODUCT OVERVIEW

Copilot Mac不是网页版的简单封装

Copilot Mac 是 Copilot 面向 macOS 的完整桌面产品。它把对话、搜索、研究与创作带进日常工作流，并通过系统入口、窗口关系、输入与反馈，形成适合 Mac 的整体体验。

产品框架定义

01 · PRODUCT LAYERS

先定义产品由哪些层共同构成

从 macOS 原生窗口开始，逐层明确背景与材质、页面内容和功能组件的归属。让每个 Feature 都建立在同一套层级关系上，而不是各自组织界面。

02 · PRODUCT FRAMEWORK

再把层级落实为稳定的产品框架

定义 Sidebar、Header、Content 与 Composer 的默认尺寸、最小边界和伸缩关系。新的内容模式可以进入同一个 Shell，不必重新发明窗口结构。

03 · RESPONSIVENESS

最后，让框架适应不同窗口与内容

以断点为边界，根据内容类型决定列数、内容宽度、沉浸模式与 Composer 行为。响应式不是按比例缩放，而是在窗口变化时保留稳定的任务关系。

04 · IN-PRODUCT GUIDE

最后，把 Dialog 的使用边界，
写成可复用的产品 Guide

Guide 依次回答三件事：当前反馈该使用哪一种组件；确认使用 Dialog 后，它是否需要阻断当前任务；最后，Dialog 里的操作应该如何分配层级。

01 · Component choice 先判断反馈组件

根据触发者、用户行动与信息持续时间，在 Toast、Inline Dialog、Modal Dialog 与 Full-screen Message 中选择。

02 · Blocking level 再判断是否需要阻断

必须暂停任务、涉及权限或数据风险时使用 Modal；需要保留上下文时使用 Inline Dialog。

03 · Action hierarchy 最后定义操作层级

每个 Dialog 只保留一个 Primary Action；可逆路径使用 Secondary；关闭为 Tertiary；不可逆风险才使用 Destructive。

让动效从分散的参数，
变成共享的产品语言

我们从产品中已有的动效出发，审计不同 Feature、组件与窗口场景中的反馈节奏，统一 timing、easing 与行为模式；再通过关键交互验证 Motion Spec，并将共性参数沉淀为 Motion Tokens。它让产品拥有更清晰、一致的响应节奏，也为下一步 code tokenization 与规模化实现建立基础。

PRODUCT REALITY

在真实代码中构建
macOS 的原生体验

macOS 的材质、窗口和系统行为无法只靠静态视觉稿定义。设计需要进入真实代码，在 SwiftUI / AppKit 的渲染环境中验证，再把结果带回产品系统。

01 · PRODUCT REALITY

先从系统材质开始，定义 Copilot 在 macOS 上的透明层级

macOS 26 是 Copilot Mac 下一阶段的重要平台基线。过去一个月，我们围绕主窗口与 Settings 的框架和布局、核心组件的 Liquid Glass，以及窗口层级做了一轮系统探索；从相对实的表面逐步提高透明度，在平台一致性与 Copilot 产品语言之间定义可继续迭代的材质基础。

但设计稿里的材质，不等于真实 Build 中的结果

同一套透明度与层级定义，在 Figma 与 SwiftUI / AppKit 的真实渲染中仍会受到系统材质、原生控件和背景内容影响，因此需要继续并排验证。

02 · THE MATERIAL GAP

Liquid Glass 不是一个可被静态稿完整描述的视觉值

macOS 26 的折射、模糊、色彩与背景内容会共同改变材质结果。只有在原生 API 中切换参数、观察窗口背后的真实内容，才能判断材质是否清晰、可读，并符合平台预期。

03 · THE OLD WAY

传统交付让材质问题，在最后一轮才被看见

设计、标注、开发与 Review 彼此串联。任何原生渲染差异都会回到流程起点，时间越紧，设计意图越容易在来回妥协中被稀释。

  1. 01Figma

    定义视觉意图

  2. 02Handoff

    补充标注和参数

  3. 03Build

    开发实现原生效果

  4. 04Review

    发现差异后返回修改

04 · DESIGN DIRECT

不只描述改变，
而是直接把它构建出来

我在 VS Code 中调用 Apple 的 Liquid Glass API，把多个材质方案放进真实 Copilot Build 进行 A/B 验证，并通过 PR 直接交付可运行的设计结果。

TYPOGRAPHY SYSTEM

为 macOS 重构字体系统

我与开发团队共同梳理 Copilot Mac 的字体层级，逐项校准字重、字距、行高与窗口缩放规则，并将原有 CMC 规范转译为更符合 macOS 阅读习惯的字体系统。通过 Vibe Coding 在真实 Build 中持续调试，让规则同时满足可读性、视觉平衡与工程实现。

  • 02参数规则

  • 03真实验证

REFLECTION

从搭建产品基础，
到思考 AI 时代的 Design System

这个项目从 Framework、Components、Motion 与 macOS 原生体验四类产品基础开始，解决不同 Feature 如何共享同一套体验。当 AI 开始参与构建界面，系统还需要进一步把这些经验转译为 AI 可以理解和执行的设计判断。真正稀缺的不再只是组件，而是何时使用、为什么这样选择，以及如何验证。

  1. 01
    WHAT 把项目成果沉淀为可调用的基础

    先让 AI 知道产品中有哪些稳定资产。

    • Framework、Components 与 Patterns
    • macOS 材质、交互状态与 Accessibility
    • Motion Tokens、品牌语言与体验原则
  2. 02
    WHEN & WHY 把产品判断写进系统

    再让 AI 理解何时使用，以及为什么这样选择。

    • 以 Dialog Guide 说明适用场景与使用边界
    • 用阻断级别与操作层级表达决策逻辑
    • 把用户任务、风险与设计意图写进规则
  3. 03
    HOW 让规则可执行，也可被验证

    最后，把规范带进生成、实现与检查流程。

    • 把 Design Rules 与 Skills 转成机器可读的约束
    • 基于真实组件，在代码中构建与调整 UI
    • 自动检查一致性、可访问性与交互质量，保留人工审核

未来的 Design System 不只是 Component Library，而是一套让 AI 能够 Understand → Decide → Build & Validate 的设计决策系统。
